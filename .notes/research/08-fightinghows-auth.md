## 4. `convex/auth.ts` — the core

All four providers are `ConvexCredentials` (NOT OAuth providers). Native SDKs do the OAuth dance on-device; the server only ever receives a token to verify. **There is no server-side OAuth redirect flow for Google/Kakao/Naver at all** — only Apple-on-Android uses a web redirect, and even that returns the ID token directly (`response_type=code id_token`).

### 4.1 `authorizeWithIdentity` — the single shared account resolver

```ts
async function authorizeWithIdentity(
  ctx: AuthorizeCtx,
  provider: 'apple' | 'google' | 'kakao' | 'naver',
  identity: VerifiedIdentity,
  fallbackName: string | undefined,
): Promise<{userId: GenericId<'users'>}> {
  const existing = await retrieveAccount<DataModel>(ctx, {
    provider,
    account: {id: identity.subject},
  }).catch(() => null);

  let userId: Id<'users'>;

  if (existing) {
    userId = existing.user._id as Id<'users'>;
  } else {
    const email = identity.email;
    const displayName =
      fallbackName ??
      identity.name ??
      email?.split('@')[0] ??
      `${DEFAULT_DISPLAY_NAME_PREFIX}${identity.subject.slice(-6)}`;

    const created = await createAccount<DataModel>(ctx, {
      provider,
      account: {id: identity.subject},
      profile: {
        email,
        name: displayName,
        image: identity.picture,
        emailVerificationTime: identity.emailVerified ? Date.now() : undefined,
      },
      // Safe: we only link when the provider itself asserts the email is
      // verified, so a second provider cannot claim someone else's account.
      shouldLinkViaEmail: shouldAutoLinkViaEmail(identity),
    });

    userId = created.user._id as Id<'users'>;
  }

  // Re-applied on EVERY sign-in, not just creation, because Convex Auth's
  // create/update callback does not run when the provider account already exists.
  if (identity.emailVerified && identity.email) {
    await ctx.runMutation(
      internal.user.actions.promoteVerifiedBootstrapAdmin,
      {userId, verifiedEmail: identity.email},
    );
  }

  // Only Naver's and Kakao's optional consent items ever populate these.
  if (
    identity.nickname !== undefined ||
    identity.gender !== undefined ||
    identity.birthday !== undefined ||
    identity.birthyear !== undefined ||
    identity.mobile !== undefined
  ) {
    await ctx.runMutation(internal.user.actions.applyProviderProfileFields, {
      userId,
      nickname: identity.nickname,
      gender: identity.gender,
      birthday: identity.birthday,
      birthyear: identity.birthyear,
      phone: identity.mobile,
    });
  }

  return {userId};
}
```

Key API surface from `@convex-dev/auth/server`: `retrieveAccount`, `createAccount`, `convexAuth`, `invalidateSessions`, `getAuthUserId`.

`DEFAULT_DISPLAY_NAME_PREFIX = '회원'` → fallback name is `회원` + last 6 chars of `sub`.

### 4.2 The four providers (each ~10 lines)

```ts
const Apple = ConvexCredentials<DataModel>({
  id: 'apple',
  authorize: async (credentials: Credentials, ctx) => {
    const verified = await verifySocialCredentials('apple', credentials);
    const apple = verified.apple;
    if (!apple) throw new Error('Apple 인증 결과를 해석하지 못했습니다.');

    const result = await authorizeWithIdentity(
      ctx, 'apple', verified.identity, verified.fallbackName,
    );

    // `apple.audience` came out of the VERIFIED token — never a client hint.
    await scheduleAppleCodeExchange(
      ctx, result.userId, apple.audience, apple.authorizationCode,
    );

    return result;
  },
});

const Google = ConvexCredentials<DataModel>({ id: 'google', authorize: async (c, ctx) => {
  const v = await verifySocialCredentials('google', c);
  return authorizeWithIdentity(ctx, 'google', v.identity, v.fallbackName);
}});
// Kakao and Naver are byte-identical apart from the id string.
```

`type Credentials = SocialCredentials = Partial<Record<string, unknown>>`.

### 4.3 `scheduleAppleCodeExchange`

```ts
async function scheduleAppleCodeExchange(
  ctx: AuthorizeCtx,
  userId: Id<'users'>,
  clientId: string,
  authorizationCode: string | undefined,
): Promise<void> {
  if (authorizationCode === undefined) return;
  if (!appleClientSecretConfig()) return;   // no signing key → nothing to spend it on

  await ctx.scheduler.runAfter(0, internal.user.actions.exchangeAppleCode, {
    userId, clientId, authorizationCode,
  });
}
```
Scheduled, never awaited: the code is single-use and expires in 5 min, but sign-in must not pay an extra Apple round trip nor fail when Apple is down.

### 4.4 `convexAuth` callbacks

```ts
export const {auth, signIn, signOut, store, isAuthenticated} = convexAuth({
  providers: [Apple, Google, Kakao, Naver],
  callbacks: {
    async afterUserCreatedOrUpdated(ctx, {userId}) {
      const db = typedDb(ctx);
      const id = userId as Id<'users'>;

      const existingProfile = await db.query('userProfiles')
        .withIndex('by_user', (q) => q.eq('userId', id)).first();
      const user = await db.get(id);
      const email = user?.email ?? '';
      const isBootstrapAdmin = shouldPromoteBootstrapAdmin(
        user?.email,
        user?.emailVerificationTime,
        bootstrapAdminEmails(process.env.BOOTSTRAP_ADMIN_EMAILS),
      );

      if (existingProfile) {
        if (isBootstrapAdmin &&
            existingProfile.role !== 'ADMIN' &&
            existingProfile.role !== 'SUSPENDED' &&
            !existingProfile.deletedAt) {
          const now = Date.now();
          await db.patch(existingProfile._id, {
            role: 'ADMIN',
            approvedAt: existingProfile.approvedAt ?? now,
            updatedAt: now,
          });
        }
        return;
      }

      await db.insert('userProfiles', {
        userId: id,
        email,
        displayName: user?.name ?? `${DEFAULT_DISPLAY_NAME_PREFIX}${String(userId).slice(-6)}`,
        role: isBootstrapAdmin ? 'ADMIN' : 'PENDING',
        approvedAt: isBootstrapAdmin ? Date.now() : undefined,
        pushEnabled: true,
        chatNotificationEnabled: true,
        postNotificationEnabled: true,
        updatedAt: Date.now(),
      });
    },

    /** A soft-deleted account must not be able to open a new session. */
    async beforeSessionCreation(ctx, {userId}) {
      const profile = await typedDb(ctx).query('userProfiles')
        .withIndex('by_user', (q) => q.eq('userId', userId as Id<'users'>)).first();

      if (profile?.deletedAt) {
        // MUST be a ConvexError: production redacts any other error's message
        // and the sign-in screen would just show "Server Error".
        throw authError('FORBIDDEN', '탈퇴한 계정입니다. 관리자에게 문의해 주세요.');
      }
    },
  },
});
```

`typedDb` helper (because auth callbacks get `GenericMutationCtx<AnyDataModel>`):
```ts
function typedDb(ctx: {db: unknown}): MutationCtx['db'] {
  return ctx.db as MutationCtx['db'];
}
```

> **BooKoo note**: FightingHows is an *approval-gated club app*, so every new account lands in `PENDING`. ## 5. Per-provider verification flow (exact)

All verification is centralized in `convex/lib/idToken.ts`. Constants:

```ts
const APPLE_ISSUER   = 'https://appleid.apple.com';
const APPLE_JWKS_URL = new URL('https://appleid.apple.com/auth/keys');

const GOOGLE_ISSUERS  = ['https://accounts.google.com', 'accounts.google.com'];
const GOOGLE_JWKS_URL = new URL('https://www.googleapis.com/oauth2/v3/certs');

const KAKAO_ISSUER   = 'https://kauth.kakao.com';
const KAKAO_JWKS_URL = new URL('https://kauth.kakao.com/.well-known/jwks.json');

const KAKAO_MAX_TOKEN_AGE_SECONDS = 10 * 60;

// Module scope on purpose: jose caches keys in-memory and refreshes on unknown
// `kid`, so no network round-trip per sign-in within the same isolate.
const appleJwks  = createRemoteJWKSet(APPLE_JWKS_URL);
const googleJwks = createRemoteJWKSet(GOOGLE_JWKS_URL);
const kakaoJwks  = createRemoteJWKSet(KAKAO_JWKS_URL);
```

### 5.1 `VerifiedIdentity` shape

```ts
export interface VerifiedIdentity {
  subject: string;          // provider `sub` — NEVER the email
  email?: string;
  emailVerified: boolean;
  name?: string;
  picture?: string;
  // Only Naver/Kakao optional consent items populate these:
  nickname?: string;
  gender?: 'M' | 'F';
  birthday?: string;        // "MM-DD"
  birthyear?: string;       // "YYYY"
  mobile?: string;          // "010-1234-5678" local form
}

export interface VerifiedAppleIdentity extends VerifiedIdentity {
  audience: string;         // the `aud` the token was actually minted for
}

export interface VerifiedSocialCredentials {
  identity: VerifiedIdentity;
  fallbackName?: string;
  apple?: {audience: string; authorizationCode?: string};
}
```

### 5.2 Apple — `verifyAppleIdToken(idToken, expectedNonce?)`

1. `appleAudiences()` = `splitEnvList(APPLE_BUNDLE_ID) ++ splitEnvList(APPLE_SERVICE_ID)`; throws if empty.
2. `jwtVerify(idToken, appleJwks, {issuer: APPLE_ISSUER, audience: audiences})` — RS256 against Apple JWKS.
3. Require `payload.sub`.
4. **Re-derive the audience by intersection** (jose only proves *some* claimed aud is allowed):
   ```ts
   const claimed = Array.isArray(payload.aud) ? payload.aud : [payload.aud];
   const audience = claimed.find((v): v is string =>
     typeof v === 'string' && audiences.includes(v));
   if (audience === undefined) throw new Error('Apple 토큰의 aud 클레임을 확인하지 못했습니다.');
   ```
5. **Nonce rule — the TOKEN decides, never the argument**:
   ```ts
   const appleNonce = asString(payload.nonce);
   if (appleNonce !== undefined && appleNonce !== expectedNonce) throw ...;
   ```
   iOS native sheet is not asked for a nonce → no claim → still valid. Android web flow always sends one → must match.
6. Returns `{subject, email, emailVerified: asBoolean(payload.email_verified), name: undefined, audience}`.

`asBoolean` exists because **Apple sends `email_verified` as the string `"true"` on some flows**:
```ts
function asBoolean(value: unknown): boolean { return value === true || value === 'true'; }
```

`isAppleServiceId(audience)` → `splitEnvList(process.env.APPLE_SERVICE_ID).includes(audience)`. Only the web flow (Services ID) sends `redirect_uri` on token exchange.

### 5.3 Google — `verifyGoogleIdToken(idToken)`

```ts
const {payload} = await jwtVerify(idToken, googleJwks, {
  issuer: GOOGLE_ISSUERS,           // both with and without scheme
  audience: googleAudiences(),      // GOOGLE_IOS_CLIENT_ID ++ ANDROID ++ WEB
});
if (!payload.sub) throw new Error('Google 토큰에 sub 클레임이 없습니다.');
return {
  subject: payload.sub,
  email: asString(payload.email),
  emailVerified: asBoolean(payload.email_verified),
  name: asString(payload.name),
  picture: asString(payload.picture),
};
```
No nonce check. Google is the **only provider that reliably yields `emailVerified === true`**, so it is effectively the anchor of the email-linking graph.

### 5.4 Kakao — `verifyKakaoIdToken(idToken, expectedNonce?)` + `fetchKakaoProfile`

Kakao issues a real OIDC ID token **once OpenID Connect is enabled on the Kakao Developers app** (must be toggled on, otherwise `idToken` comes back as `""` on iOS).

```ts
// Signature, issuer, and AGE first. `aud` checked by hand so the error can
// name the token's actual app key.
const {payload} = await jwtVerify(idToken, kakaoJwks, {
  issuer: KAKAO_ISSUER,
  maxTokenAge: KAKAO_MAX_TOKEN_AGE_SECONDS,   // 10 minutes
});

const allowed  = kakaoAudiences();  // KAKAO_NATIVE_APP_KEY ∪ KAKAO_REST_API_KEY
const claimed  = claimedAudiences(payload.aud);
const audience = claimed.find((v) => allowed.includes(v));
if (audience === undefined) throw new Error(
  `카카오 앱 키가 서버와 맞지 않습니다. 토큰 aud=${claimed.map(maskAppKey).join(',') || '(없음)'} 서버=${allowed.map(maskAppKey).join(',')}`,
);
if (!payload.sub) throw new Error('Kakao 토큰에 sub 클레임이 없습니다.');

// jose has no nonce option. TOKEN decides — keying on `expectedNonce` would let
// a replayer skip the check by omitting the argument.
const nonce = asString(payload.nonce);
if (nonce !== undefined && nonce !== expectedNonce) throw ...;

return {
  subject: payload.sub,
  email: asString(payload.email),
  emailVerified: false,       // ← Kakao's ID token has NO email_verified claim
  name: asString(payload.nickname),
  picture: asString(payload.picture),
};
```

`maskAppKey(v)` → `${v.slice(0,4)}…${v.slice(-4)}` (or `(len N)` when ≤8) so the error never leaks a full key.

`maxTokenAge: 10min` is the **only replay bound on the Android KakaoTalk hand-off path**, which returns a token carrying no `nonce` at all.

Then, if the client also sent an `accessToken`, `verifySocialCredentials` calls `fetchKakaoProfile(accessToken, identity.subject)`:

```
GET https://kapi.kakao.com/v2/user/me
Authorization: Bearer <accessToken>
```
- `body.id` is a **JSON number** here but a **string** in the ID token's `sub` → coerced with `String(body.id)`.
- **`expectedSubject` is mandatory**: Kakao's `/v2/user/me` does NOT report the `app_id` the access token was minted for. A foreign app's token resolves to a different `id`, so a mismatch throws `'카카오 토큰이 서로 다른 사용자를 가리킵니다.'`. This is what stops a foreign token from upgrading anyone's `emailVerified`.
- Email verification requires **both** flags:
  ```ts
  const emailVerified =
    account?.is_email_valid === true && account?.is_email_verified === true;
  ```
  (`is_email_valid` goes false when the address was later taken over by another Kakao account.)
- Optional consent items read off `body.kakao_account`: `email`, `gender` (`'male'|'female'` → `'M'|'F'`), `birthday` (Kakao sends `"MMDD"` no separator → reformatted to `"MM-DD"`), `birthyear`, `phone_number` (Kakao sends `"+82 10-1234-5678"` → normalized `raw.replace(/^\+82\s*/, '0')`).

The merged result in `verifySocialCredentials`:
```ts
identity: profile ? {
  ...identity,
  email: identity.email ?? profile.email,
  emailVerified: profile.emailVerified,   // upgraded from the user API
  gender: profile.gender,
  birthday: profile.birthday,
  birthyear: profile.birthyear,
  mobile: profile.mobile,
} : identity
```

### 5.5 Naver — `verifyNaverAccessToken(accessToken)`

**Naver has no OIDC ID token.** The native SDK hands over a bare OAuth access token, so there is no signature to verify — the only way to learn who owns it is to spend it:

```
GET https://openapi.naver.com/v1/nid/me
Authorization: Bearer <accessToken>
```
- Success requires `body.resultcode === '00'`; anything else throws.
- Failure bodies are inconsistent: documented `{errorCode, errorMessage}`, but the gateway also emits `{status, error, path}` → falls back to the HTTP status code.
- `subject = asString(body.response.id)`.
- Fields read: `email`, `name ?? nickname`, `profile_image` (→ `picture`), `nickname`, `gender` (`'M'|'F'`; Naver also sends `'U'` = declined → dropped), `birthday` (`"MM-DD"`, already separated), `birthyear`, `mobile ?? mobile_e164`.

**Documented security gap (copy this comment verbatim into BooKoo):**
> The token is not proven to have been issued to *our* Naver app. Neither `oauth2.0/authorize`, `oauth2.0/token`, nor the profile endpoint reports the `client_id` a token was minted for, so a token from somebody else's Naver app is accepted here.
> Two properties keep that short of account takeover:
> 1. `response.id` is documented as unique **per application**, so a foreign app's token yields an id that cannot match one already stored for us.
> 2. **`emailVerified` stays `false`**, which keeps `authorizeWithIdentity` from linking this identity into an existing account by email.
>
> **Never flip (2) to true.**

### 5.6 The single boundary — `verifySocialCredentials(provider, credentials)`

Shared by sign-in **and** account linking, so a credential accepted for linking gets the exact same signature/issuer/audience/nonce/profile checks as sign-in.

Credential keys read (all `unknown` → validated):
| provider | required | optional |
|---|---|---|
| apple | `idToken` | `nonce`, `authorizationCode`, `name` |
| google | `idToken` | `name` |
| kakao | `idToken` | `nonce`, `accessToken`, `name` |
| naver | `accessToken` | `name` |

Helpers: `requireCredentialString(value, field)` (throws `` `${field} 값이 필요합니다.` ``), `optionalCredentialString` (trims, empty → undefined), `splitEnvList` (comma-split, trim, drop empties).

## 6. Account-linking policy

### 6.1 Why key by `sub`, not email

From `convex/auth.ts` header comment (verbatim):
> Accounts are keyed by the provider `sub` rather than the email — Apple's private relay emails can change, but `sub` is stable for the lifetime of the Apple ID ↔ app relationship.

So `authAccounts.providerAccountId === identity.subject`, always. Email is *only* a linking hint, never an identity.

### 6.2 `shouldAutoLinkViaEmail` — when auto-merge fires

`shared/authPolicy.ts` (verbatim, whole file's relevant parts):

```ts
interface EmailIdentity {
  email?: string;
  emailVerified: boolean;
}

export function bootstrapAdminEmails(value: string | undefined): string[] {
  return (value ?? '')
    .split(',')
    .map((email) => email.trim().toLowerCase())
    .filter((email) => email.length > 0);
}

export function shouldAutoLinkViaEmail(identity: EmailIdentity): boolean {
  return identity.emailVerified && Boolean(identity.email?.trim());
}

export function shouldPromoteBootstrapAdmin(
  email: string | undefined,
  emailVerificationTime: number | undefined,
  configuredEmails: string[],
): boolean {
  return (
    email !== undefined &&
    emailVerificationTime !== undefined &&
    configuredEmails.includes(email.trim().toLowerCase())
  );
}

function normalizedEmail(value: string | undefined): string {
  return value?.trim().toLowerCase() ?? '';
}

/**
 * Linking already proves possession of both provider identities. Email still
 * has to match on both user rows so a provider account owned by somebody else
 * can never be absorbed into the current member.
 */
export function hasMatchingAccountEmails(
  currentEmailValue: string | undefined,
  otherEmailValue: string | undefined,
  credentialEmailValue: string | undefined,
): boolean {
  const currentEmail = normalizedEmail(currentEmailValue);
  const otherEmail = normalizedEmail(otherEmailValue);
  const credentialEmail = normalizedEmail(credentialEmailValue);

  return (
    currentEmail.length > 0 &&
    currentEmail === otherEmail &&
    (credentialEmail.length === 0 || credentialEmail === currentEmail)
  );
}
```

**Effective auto-link truth table** (what `shouldLinkViaEmail` gets on `createAccount`):

| provider | `emailVerified` source | auto-links by email? |
|---|---|---|
| Google | `email_verified` claim in ID token | **yes** (basically always true) |
| Apple | `email_verified` claim (may be string `"true"`) | **yes** — including private-relay addresses |
| Kakao | `/v2/user/me` `is_email_valid && is_email_verified` — **only if the client sent `accessToken`** | yes when both flags hold, else **no** |
| Naver | hard-coded `false` | **never** |

So: Google + Apple + verified-Kakao with the same address collapse into one `users` row automatically. Naver always creates a fresh row, and must be joined manually on the 연결된 계정 screen.

### 6.3 Manual linking — `api.user.actions.linkAccount` (public action)

```ts
export const linkAccount = action({
  args: {provider: socialProviderValidator, credentials: socialCredentialsValidator},
  returns: v.object({merged: v.boolean()}),
  handler: async (ctx, args) => {
    const userId = await requireActionUserId(ctx);
    // verify FIRST (network), then mutate
    verified = await verifySocialCredentials(args.provider, args.credentials);
    // ...on failure: log the real error, throw a generic ConvexError to the client
    const result = await ctx.runMutation(internal.user.actions.linkVerifiedAccount, {
      userId, provider: args.provider,
      providerAccountId: verified.identity.subject,
      ...(verified.identity.email ? {credentialEmail: verified.identity.email} : {}),
    });
    if (verified.identity.emailVerified && verified.identity.email) { /* promote */ }
    if (result.invalidatedUserId !== null) { await invalidateSessions(ctx, {userId: result.invalidatedUserId}); }
    if (args.provider === 'apple' && verified.apple?.authorizationCode && appleClientSecretConfig()) {
      await ctx.scheduler.runAfter(0, internal.user.actions.exchangeAppleCode, {
        userId, clientId: verified.apple.audience,
        authorizationCode: verified.apple.authorizationCode,
      });
    }
    return {merged: result.merged};
  },
});
```

### 6.4 `linkVerifiedAccount` (internalMutation) — decision tree

1. `requireProfileOf(ctx, userId)` — recheck the profile still exists (closes the "deleted while waiting on the provider's network" gap).
2. Look up `authAccounts` by index `providerAndAccountId` (`.take(2)`).
3. **Idempotency**: if every matching row already belongs to `userId` → `{merged:false, invalidatedUserId:null}`. Retrying a verified request must not create a second row.
4. `otherOwners.length > 1` → `FORBIDDEN` "연결 정보가 중복되어 있어 관리자 확인이 필요해요."
5. `otherOwners.length === 1` (the provider identity belongs to another user):
   - Requires `hasMatchingAccountEmails(currentProfile.email, otherProfile.email, credentialEmail)` **and** other profile exists and isn't deleted, else `FORBIDDEN` "이미 다른 회원에게 연결되어 있어요."
   - Either side `SUSPENDED` → refuse.
   - `isDisposablePendingProfile(other)` → **auto-merge** via `mergeDisposableProfile`.
   - else if current is `PENDING` → "기존에 사용하던 계정으로 로그인한 뒤 연결해 주세요."
   - else → "두 계정에 모두 활동 기록이 있어 자동으로 합칠 수 없어요."
6. Otherwise: if the current user already has a row for this provider → refuse ("먼저 기존 연결을 해제해 주세요") — **one account per provider per user**.
7. `ctx.db.insert('authAccounts', {userId, provider, providerAccountId})`.

`isDisposablePendingProfile` = `role === 'PENDING' && !deletedAt` **and** eleven indexed `.first()` reads all return `null` (memberships, chatRooms, posts, postComments, postLikes, shortsLikes, shortsFavorites, shortsComments, pushTokens, notifications, appleRefreshTokens). BooKoo's equivalent set would be ledgers/entries/invites.

`mergeDisposableProfile`:
- `.take(LINKED_ACCOUNT_SCAN_LIMIT)` (=20) on both users' `authAccounts` via `userIdAndProvider`; hitting the cap → refuse.
- Provider conflict between the two sets → refuse, naming the provider via `SOCIAL_PROVIDER_LABELS`.
- `ctx.db.patch(account._id, {userId: canonical.userId})` for each disposable account row.
- **Clears the disposable `users` row's email**: `{email: undefined, emailVerificationTime: undefined}` — "Keeping a second verified `users.email` row would make Convex Auth's uniqueness check refuse every later email-based provider link."
- Soft-deletes the disposable profile: `{email: '', deletedAt: now, updatedAt: now}`.

## 7. Apple: refresh-token exchange & revocation (App Store 5.1.1(v))

### 7.1 Why

Any app offering Sign in with Apple must let the user revoke the grant on account deletion. Revocation needs the **refresh token**, which is only obtainable by spending the one-time `authorizationCode` within 5 minutes of sign-in.

### 7.2 `convex/lib/appleTokens.ts` — full mechanics

```ts
const APPLE_ISSUER     = 'https://appleid.apple.com';
const APPLE_TOKEN_URL  = 'https://appleid.apple.com/auth/token';
const APPLE_REVOKE_URL = 'https://appleid.apple.com/auth/revoke';
const CLIENT_SECRET_TTL_SECONDS = 5 * 60;   // Apple allows 6 months; we mint per-request
```

**Config gate** — everything is a silent no-op until all three env vars land:
```ts
export function appleClientSecretConfig(): AppleClientSecretConfig | null {
  const teamId     = readEnv('APPLE_TEAM_ID');
  const keyId      = readEnv('APPLE_KEY_ID');
  const privateKey = readEnv('APPLE_PRIVATE_KEY');
  if (!teamId || !keyId || !privateKey) return null;
  // A `.p8` is multi-line and most env-var entry paths flatten it.
  return {teamId, keyId, privateKey: privateKey.replace(/\\n/g, '\n')};
}
```

**Redirect URI** (must match the Services ID's Return URL character-for-character):
```ts
export function appleWebRedirectUri(): string {
  return `${process.env.CONVEX_SITE_URL ?? ''}${APPLE_CALLBACK_PATH}`;
}
```

**Client secret = a signed ES256 JWT** (Apple takes this where other providers take a static secret):
```ts
export async function createAppleClientSecret(config, clientId): Promise<string> {
  const key = await importPKCS8(config.privateKey, 'ES256');
  const issuedAt = Math.floor(Date.now() / 1000);
  return new SignJWT({})
    .setProtectedHeader({alg: 'ES256', kid: config.keyId})
    .setIssuer(config.teamId)
    .setIssuedAt(issuedAt)
    .setExpirationTime(issuedAt + CLIENT_SECRET_TTL_SECONDS)
    .setAudience(APPLE_ISSUER)
    .setSubject(clientId)     // bundle id (iOS) or Services ID (Android web)
    .sign(key);
}
```

**Code → refresh token**:
```ts
export async function exchangeAppleAuthorizationCode(config, clientId, code, redirectUri?) {
  const form = new URLSearchParams({
    client_id: clientId,
    client_secret: await createAppleClientSecret(config, clientId),
    code,
    grant_type: 'authorization_code',
  });
  if (redirectUri !== undefined) form.set('redirect_uri', redirectUri);
  const {ok, payload, status} = await postToApple(APPLE_TOKEN_URL, form);
  if (!ok) throw new Error(`Apple 토큰 교환에 실패했습니다. (${appleErrorCode(payload, status)})`);
  return asString(asRecord(payload)?.refresh_token);
}
```
`redirect_uri` is sent **only for the web/Services-ID flow**; the native bundle-id flow must omit it.

**Revoke** (RFC 7009):
```ts
export async function revokeAppleRefreshToken(config, clientId, refreshToken) {
  const form = new URLSearchParams({
    client_id: clientId,
    client_secret: await createAppleClientSecret(config, clientId),
    token: refreshToken,
    token_type_hint: 'refresh_token',
  });
  const {ok, payload, status} = await postToApple(APPLE_REVOKE_URL, form);
  if (ok) return;
  throw new Error(`Apple 토큰 폐기에 실패했습니다. (${appleErrorCode(payload, status)})`);
}
```
> Apple answers **200 with an empty body** both for a token it just killed and for one it does not recognise (verified with a junk token). So 200 means "Apple accepted the request", never "the grant is provably gone". Only non-200 (bad client id, unverifiable secret) is worth retrying.

`postToApple` posts `application/x-www-form-urlencoded`, catches transport errors into `'Apple 서버에 연결하지 못했습니다.'`, and tolerates a non-JSON body.

### 7.3 Storage — `appleRefreshTokens` table

```ts
export const appleRefreshTokensTable = defineTable({
  userId: v.id('users'),
  clientId: v.string(),      // bundle id on iOS, Services ID on Android web — DIFFERENT values, so stored not guessed
  refreshToken: v.string(),  // SECRET. Must never reach a client.
  updatedAt: v.number(),
}).index('by_user_and_client', ['userId', 'clientId']);
```
`APPLE_TOKEN_SCAN_LIMIT = 8` (a user holds at most one row per Apple `client_id`, so two).

`saveAppleRefreshToken` upserts on `(userId, clientId)` — Apple mints a fresh refresh token on every authorization and only the newest is worth keeping.
`listAppleRefreshTokens` is an **internalQuery** returning `{_id, clientId, refreshToken}`.
`dropAppleRefreshTokens` **hard-deletes** — "the row *is* the secret, so a `deletedAt` would leave behind exactly the value we were asked to get rid of."

### 7.4 End-to-end flow

**Acquire (sign-in or link):**
1. Client → `authorizationCode` (iOS: `AppleAuthentication.signInAsync().authorizationCode`; Android: the `code` param out of Apple's `form_post`).
2. `authorize` → `scheduleAppleCodeExchange` → `ctx.scheduler.runAfter(0, internal.user.actions.exchangeAppleCode, {userId, clientId, authorizationCode})`.
3. `exchangeAppleCode` (internalAction): bail if `!appleClientSecretConfig()`; call `exchangeAppleAuthorizationCode(config, clientId, code, isAppleServiceId(clientId) ? appleWebRedirectUri() : undefined)`; save. **Failures are swallowed with `console.error`** — "Losing the token costs us the ability to revoke later, but failing the sign-in over it would cost the user the account entirely."

**Revoke (탈퇴 or unlink apple):**
1. `user.mutations.deleteAccount` (or `unlinkAccount({provider:'apple'})`) → `ctx.scheduler.runAfter(0, internal.user.actions.revokeAppleTokens, {userId})`.
2. `revokeAppleTokens` (internalAction): `listAppleRefreshTokens` → if none, done; if `!appleClientSecretConfig()`, return **keeping the rows** so the grant can be cleaned up once the key lands. Loop each row, `revokeAppleRefreshToken`, collect the successful ids, `dropAppleRefreshTokens({ids})`. A row that survives a failure **is** the record that this grant still owes Apple a revocation.
3. Scheduled, not awaited: a mutation cannot reach the network, and 탈퇴 has already committed — its outcome must not be undone.

### 7.5 Apple-on-Android web flow (`convex/appleWeb.ts`)

Sign in with Apple has **no native Android SDK**, and Apple refuses to redirect to a custom URL scheme — only an https `redirect_uri` registered against a **Services ID**. So:

```ts
const APP_REDIRECT_SCHEME = 'fightinghows://apple-callback';  // fixed literal — a request-chosen target would be an open redirector

export const appleCallback = httpAction(async (_ctx, request) => {
  const body = await request.text().catch(() => null);
  if (body === null) return new Response('잘못된 요청입니다.', {status: 400});

  const posted = new URLSearchParams(body);   // form_post ⇒ x-www-form-urlencoded
  const params = new URLSearchParams();

  // `error=user_cancelled_authorize` must reach the app too, or the tab just sits there.
  for (const key of ['id_token', 'code', 'state', 'user', 'error']) {
    const value = posted.get(key);
    if (value !== null && value.length > 0) params.set(key, value);
  }

  // Fragment, not query: OAuth implicit-response convention, keeps the token out
  // of anything that records URLs as addresses.
  return new Response(null, {
    status: 302,
    headers: {Location: `${APP_REDIRECT_SCHEME}#${params.toString()}`},
  });
});
```
`URLSearchParams` is used because **`FormData` is not typed in the Convex runtime**.

Threat note (verbatim intent): the endpoint is unauthenticated and forwards verbatim, but the redirect lands on whichever device made the request and the ID token is still JWKS-verified and nonce/state-matched before it becomes a session. Forging a request gains an attacker a redirect to their own app and nothing else.

### 10.3 `useSocialSignIn.ts` — native SDK calls

One-time lazy configuration guards (`let googleConfigured = false`, `let naverInitialized = false`):


**Cancellation is modelled as `class CancelledError extends Error {}` and never surfaced to the user.** The `run(provider, task)` wrapper sets `pending`, catches, swallows `CancelledError`, `logError`s the rest, and toasts a Korean fallback.

| provider | SDK call | cancel detection |
|---|---|---|
| Apple (iOS) | `AppleAuthentication.signInAsync({requestedScopes:[FULL_NAME, EMAIL]})` | `error.code === 'ERR_REQUEST_CANCELED'` |
| Apple (Android) | `WebBrowser.openAuthSessionAsync(authorizeUrl, appRedirect)` | `result.type !== 'success'`, or `params.get('error')` |
| Google | `GoogleSignin.hasPlayServices({showPlayServicesUpdateDialog:true})` then `GoogleSignin.signIn()` | `isErrorWithCode(e) && (e.code === statusCodes.SIGN_IN_CANCELLED \|\| statusCodes.IN_PROGRESS)`, plus `response.type === 'cancelled'` |
| Kakao | `kakaoLogin({nonce})` from `@react-native-seoul/kakao-login` | `/cancel/i.test(error.message)` — **unreliable**, see below |
| Naver | `NaverLogin.login()` | `!result.isSuccess && result.failureResponse?.isCancel` (Naver reports failure in the resolved value, not a rejection) |

**Kakao cancellation caveat (verbatim):**
> The Kakao bridge rejects *every* failure with the same `RNKakaoLogins` code, so the message is the only signal. On Android that message is `ClientErrorCause.Cancelled`'s `@Description` ("user cancelled."), read off the enum by reflection — a build that strips runtime annotations degrades it to "Client-side error" and the cancel is missed. On iOS it is missed always: `SdkError` is a bare `enum: Error` with no `LocalizedError` conformance.

**Apple web flow (Android)** — full URL construction:
```ts
const state = randomUUID();   // from expo-crypto
const nonce = randomUUID();

const authorizeUrl =
  'https://appleid.apple.com/auth/authorize?' +
  new URLSearchParams({
    client_id: serviceId,
    redirect_uri: redirectUri,
    response_type: 'code id_token',   // ID token arrives in the authorize response — no token exchange on the critical path
    response_mode: 'form_post',       // forced by asking for name/email
    scope: 'name email',
    state,
    nonce,
  }).toString();

const result = await WebBrowser.openAuthSessionAsync(authorizeUrl, appRedirect);
if (result.type !== 'success') throw new CancelledError();

// The callback puts everything in the FRAGMENT — `URL.searchParams` would be empty.
const fragment = result.url.split('#')[1] ?? '';
const params = new URLSearchParams(fragment);
if (params.get('error')) throw new CancelledError();
if (params.get('state') !== state) throw new Error('Apple 로그인 응답이 올바르지 않아요.');

const idToken = params.get('id_token');
const authorizationCode = params.get('code');   // optional — missing code never blocks sign-in
await authorize('apple', {idToken, nonce, ...(authorizationCode ? {authorizationCode} : {}), ...parseAppleUserName(params)});
```

`parseAppleUserName(params)` JSON-parses the `user` form field (`{name:{familyName,givenName}}`), joins **Korean order** `familyName + givenName` with no separator, and returns `{}` on any malformation (a bad JSON blob must not fail a sign-in).

**iOS Apple name** — same order:
```ts
const name = [credential.fullName?.familyName, credential.fullName?.givenName].filter(Boolean).join('');
```
Apple hands over the full name **exactly once, on the very first authorization** — hence the `name` credential field and the `fallbackName` plumbing all the way to `createAccount`.

**Kakao**: `nonce` freshly minted per attempt; `token.idToken` may be `""` on iOS when OIDC is off for the app → treated as missing; `accessToken` forwarded so the backend can ask Kakao about email verification.

**Naver**: only `{accessToken}` is sent.

### 10.5 Native SDK release (sign-out / unlink)

```ts
async function releaseSocialSdk(provider, mode: 'logout' | 'unlink') {
  const unlinking = mode === 'unlink';
  if (provider === 'apple') return;    // device has no client secret; backend revokes
  if (provider === 'kakao')  { await (unlinking ? kakaoUnlink() : kakaoLogout()); return; }
  if (provider === 'naver')  { initializeNaverOnce(...); await (unlinking ? NaverLogin.deleteToken() : NaverLogin.logout()); return; }
  configureGoogleOnce();               // native session outlives the process
  await (unlinking ? GoogleSignin.revokeAccess() : GoogleSignin.signOut());
}

export function signOutSocialSessions(): Promise<void> { return releaseSocialSdks('logout'); }
export function disconnectSocialAccount(p): Promise<void> { return releaseSocialSdk(p, 'unlink'); }
export function disconnectSocialAccounts(): Promise<void> { return releaseSocialSdks('unlink'); }
```

### 10.8 `deleteAccount` server side (`convex/user/mutations.ts`)

1. `requireProfile`.
2. Refuse if this is the **last non-deleted ADMIN** (`ADMIN_SCAN_LIMIT`-capped `by_role` scan).
3. `ctx.db.patch(profile._id, {deletedAt: now, updatedAt: now})` — **soft delete**.
4. Hard-delete every `pushTokens` row (no `deletedAt` on that table; a survivor would keep pushing to a device whose account is gone).
5. `ctx.scheduler.runAfter(0, internal.user.actions.revokeAppleTokens, {userId})`.

`unlinkAccount({provider})`:
- `.take(LINKED_ACCOUNT_SCAN_LIMIT)` on `userIdAndProvider`.
- No-op if already gone.
- **Refuses to drop the last usable provider**: `if (target.length === usableAccounts.length) throw FORBIDDEN '마지막 로그인 수단은 해제할 수 없습니다.'`
- **Hard delete** the `authAccounts` rows — "the row *is* the credential, so a `deletedAt` would leave behind exactly the thing being revoked, and the library's `providerAndAccountId` lookup would still find it."
- If `provider === 'apple'`, schedules `revokeAppleTokens`.

### 10.10 Session state machine (`src/hooks/useSession.ts`)

```js

const fs = require('fs/promises');
const path = require('path');

const KAKAO_MARKER = '# Kakao SDK (reflection used by models and Retrofit APIs)';
const RETROFIT_MARKER = '# Retrofit 2.9 full-mode compatibility required by the Kakao SDK';

const KAKAO_PROGUARD_RULES = `
${KAKAO_MARKER}
-keep class com.kakao.sdk.**.model.* { <fields>; }
-keep interface com.kakao.sdk.** { *; }
-keepattributes Signature,InnerClasses,EnclosingMethod
-keepattributes RuntimeVisibleAnnotations,RuntimeInvisibleAnnotations,RuntimeVisibleParameterAnnotations,RuntimeInvisibleParameterAnnotations,AnnotationDefault
-keep class * extends com.google.gson.TypeAdapter

# Optional TLS providers referenced by OkHttp.
-dontwarn org.bouncycastle.jsse.**
-dontwarn org.conscrypt.*
-dontwarn org.openjsse.**
`;

const RETROFIT_PROGUARD_RULES = `
${RETROFIT_MARKER}
# Retrofit 2.9 does not include the R8 full-mode rules added in later releases.
# Keep service inheritance and generic return types used by the Kakao SDK.
-if interface * { @retrofit2.http.* <methods>; }
-keep,allowobfuscation interface <1>
-if interface * { @retrofit2.http.* <methods>; }
-keep,allowobfuscation interface * extends <1>
-keep,allowobfuscation,allowshrinking class kotlin.coroutines.Continuation
-if interface * { @retrofit2.http.* public *** *(...); }
-keep,allowoptimization,allowshrinking class <3>
-keep,allowobfuscation,allowshrinking class retrofit2.Response
`;

module.exports = function withKakaoProguard(config) {
  return withDangerousMod(config, ['android', async (modConfig) => {
    const proguardPath = path.join(
      modConfig.modRequest.platformProjectRoot, 'app', 'proguard-rules.pro',
    );
    const existing = await fs.readFile(proguardPath, 'utf8');
    let next = existing.trimEnd();

    if (!existing.includes(KAKAO_MARKER))    next += `\n${KAKAO_PROGUARD_RULES}`;
    if (!existing.includes(RETROFIT_MARKER)) next += `\n${RETROFIT_PROGUARD_RULES}`;
    if (next !== existing.trimEnd()) await fs.writeFile(proguardPath, `${next}\n`);

    return modConfig;
  }]);
};
```

```ts
    apiKey: RESEND_API_KEY,          // process.env.AUTH_RESEND_KEY

    async generateVerificationToken() {

    },
    async sendVerificationRequest(
      {identifier: email, provider, token}: SendVerificationRequestArgs,
```

`convex/utils/resendClient.ts` — hand-rolled HTTP, no SDK dependency:
```ts
const RESEND_API_ENDPOINT = 'https://api.resend.com/emails';

export async function sendResendEmail(apiKey: string | undefined, payload: ResendEmailPayload) {
  if (!isProduction) {           // process.env.ENVIRONMENT !== 'production'
    console.info('[resend] Skipping email delivery in non-production env', {
      to: payload.to, subject: payload.subject, textPreview: payload.text,
    });
    return {skipped: true};      // the OTP is printed in the Convex log instead
  }
  if (!apiKey) throw new Error('Resend API key is not configured');

  const response = await fetch(RESEND_API_ENDPOINT, {
    method: 'POST',
    headers: {Authorization: `Bearer ${apiKey}`, 'Content-Type': 'application/json'},
    body: JSON.stringify(payload),
  });
  let data: any = null;
  try { data = await response.json(); } catch {}
  if (!response.ok || data?.error) {
    throw new Error(data?.error?.message ?? data?.message ?? `Resend request failed with status ${response.status}`);
  }
  return data;
}
```

- social → `providerAccountId = identity.subject`
- Email/OTP → `providerAccountId = the email address`

Convex Auth's `Email` provider sets `users.email` and stamps `emailVerificationTime` when the code verifies. Because the social path passes `shouldLinkViaEmail: shouldAutoLinkViaEmail(identity)`, a **later** social sign-in with a provider-verified address (Google/Apple/verified-Kakao) automatically lands on the same `users` row created by OTP. The reverse direction (OTP after a social account already exists) is handled by Convex Auth's own email-uniqueness lookup on `users.email`.

Gaps to plan for:
1. **Naver/unverified-Kakao will NOT auto-merge with an OTP account.** They must go through the manual `linkAccount` path (§6.3), whose `hasMatchingAccountEmails` check requires both stored profile emails to agree.
2. `mergeDisposableProfile`'s trick of clearing the disposable `users.email`/`emailVerificationTime` exists precisely because "keeping a second verified `users.email` row would make Convex Auth's uniqueness check refuse every later email-based provider link." Keep that.
3. Add `'otp'` (or your provider ids) to the union that `socialProviderValidator` / `SOCIAL_PROVIDER_LABELS` / `isSocialProvider` cover, or the linked-accounts screen will silently drop OTP rows and `unlinkAccount`'s "last login method" guard will miscount (`usableAccounts` filters on `isSocialProvider`).
